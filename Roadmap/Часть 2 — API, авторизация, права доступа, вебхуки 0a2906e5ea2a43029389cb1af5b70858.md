## Блок 0 — три блокера

Выношу отдельно: каждый из трёх сам по себе достаточен, чтобы не выпускать систему в продакшен.

### A. [C] `require_admin` не проверяет никаких прав

В системе объявлено двенадцать прав, и есть красивый `require_permission(...)`. Но часть ручек сидит на `require_admin`, который проверяет **только факт авторизации**, а не право.

**Следствие:** сотрудник с базовым набором `DEFAULT_STAFF = (codes.view, codes.submit)` может вызвать ручки, на которые ему прав не выдавали. Критичнейшая — `POST /api/admin/pts/grant`: печать PTS без ограничения суммы и без права `pts.grant`.

А право `pts.grant` при этом **декоративное**: оно честно проверяется в `manage.py`, но рядом живёт вторая ручка той же операции без проверки. Фронтенд прячет разделы по `data-perm` — но прятание навигации никогда не было защитой.

### B. [C] `GET /api/console/clubs` отдаёт `webhook_token` в открытом виде

Токен вебхука — это ключ к начислению минут, выполнению ачивок и привязке телефонов. Он попадает:

- в ответ API любому с `clubs.edit`
- в таблицу клубов в админке **целиком, без маски** (часть 4) — то есть на экран стойки, где его видит любой прохожий

С этим токеном можно самостоятельно выставить себе `duration_minutes = 100000` (границы нет, см. часть 5) и мгновенно получить группу «Легенда» со всеми минутными ачивками.

### C. [C] `POST /api/console/test/session-start` и `session-end` без права и без запрета в проде

Ручки идут тем же путём, что реальные вебхуки — то есть пишут в продакшен-данные: создают сессии, начисляют минуты, выполняют ачивки, зачитывают рефералов. Право `test.tools` объявлено, но на этих ручках не проверяется, а в админке это верхнеуровневый пункт меню без предупреждающего баннера.

Плюс `_ensure_test_user` — четвёртая независимая реализация get-or-create пользователя: через панель можно **создавать гостевые аккаунты с произвольным `telegram_id`**.

## 1. Авторизация гостя (`auth.py`)

### Верифицировано как корректное

Проверка подписи `initData` построена правильно:

1. `secret_key = HMAC_SHA256(key="WebAppData", msg=bot_token)`
2. `data_check_string` — отсортированные пары `key=value` через `\n`
3. Из словаря извлекается **только** `hash` (не `signature`, не всё подряд)
4. Сравнение через `compare_digest`
5. `INIT_DATA_MAX_AGE_SECONDS = 24*60*60` — проверка `auth_date`

Это сделано верно, и это самая важная точка безопасности гостевого контура.

### [H] `INIT_DATA_MAX_AGE_SECONDS` = 24 часа

Сутки — очень широкое окно для переиспользования перехваченного `initData`. Строка передаётся в заголовке на **каждый** запрос и не ротируется. Рекомендую 1–3 часа либо обмен `initData` на короткий серверный токен при старте сессии.

### [H] `get_or_create_user` коммитит внутри зависимости

Зависимость авторизации — читающая операция, но она создаёт пользователя и фиксирует транзакцию до того, как выполнился сам хендлер. Тот же системный паттерн, что `overview()` и `expire_due()`.

### [M] Гонка при первом входе

SELECT-then-INSERT без обработки `IntegrityError`. Два параллельных запроса при первом открытии мини-аппа (а он делает четыре запроса в `refreshAll`) → дубль либо 500.

### [M] `dev_allow_fake_auth` не логируется при срабатывании

Если флаг включён, каждый подменённый вход проходит молча. Нет ни метрики, ни записи в журнал.

## 2. Авторизация админа (`admin_auth.py`)

### Верифицировано как корректное

- PBKDF2 с `_PBKDF2_ITERATIONS = 310_000` — актуальный параметр OWASP
- Подпись сессии через HMAC, сравнение через `compare_digest`
- `httponly`, `samesite="lax"` на `bh_admin_session`
- Порядок «сначала подпись, потом `int()`» — верный
- **CSRF оцениваю как приемлемо:** `samesite=lax` блокирует кросс-сайтовые POST, а изменяющих состояние GET-ручек нет. Но это должно быть **записанным решением**, а не случайным свойством

### [C] Нет rate-limit на входе

`POST /api/console/auth/login` можно дёргать бесконечно. Два следствия:

1. **Перебор пароля** при дефолтном `change-me-now` — вопрос одного запроса
2. **CPU-DoS**: `AdminLoginRequest.password` без `max_length` (часть 5) → пароль на мегабайт прогоняется через PBKDF2 310k итераций. Несколько параллельных запросов — и однопоточный процесс лежит

### [H] Сессия не отзывается никогда и ничем

Пейлоад сессии — `f"{admin_id}:{expires}:{sign}"` в base64url. В нём нет ни версии пароля, ни идентификатора сессии, ни списка отозванных. Следствия:

- Смена пароля **не выкидывает** уже вошедшие сессии (TTL 12 ч)
- Сброс пароля владельцем тоже не выкидывает уволенного сотрудника
- Удаление учётки + переиспользование rowid в SQLite → **старая кука аутентифицирует нового админа** (см. часть 5)

### [H] `secure=True` на куке не выставляется

Кука сессии и `bh_demo_gate` уедут по HTTP, если стенд поднят без TLS или за кривым прокси.

### [M] Нет защиты от timing-атаки на существование логина

При неверном логине PBKDF2 не вызывается вовсе → ответ приходит на порядок быстрее. Логины админов перебираются без паролей.

### [M] `admin_session_ttl_hours=12` без продления и без предупреждения

Сотрудник на смене 12+ часов вылетит посреди работы, и следующий же запрос отдаст 401, который админка превратит в экран входа без сохранения контекста (часть 4).

### [M] `X-Admin-Token` и кука — два параллельных контура авторизации

Статичный `admin_token` из `.env` даёт доступ к `/api/admin/*` без всяких ролей, без журнала действий и без возможности отозвать. Две модели доступа на одну систему — вторая должна быть убрана.

## 3. Модель прав (`permissions.py`)

Объявленные права: `codes.view`, `codes.submit`, `codes.approve`, `users.view`, `pts.grant`, `catalog.edit`, `clubs.edit`, `reports.view`, `logs.view`, `test.tools`, `admins.manage`, `oasys.view`.

`OWNER_ONLY = {admins.manage, codes.approve}`, `DEFAULT_STAFF = (codes.view, codes.submit)`.

### [C] Восемь из двенадцати прав фактически не проверяются

Модель прав выглядит продуманной, и в `manage.py` она действительно работает. Но там, где стоит `require_admin`, право становится украшением. Пользователь видит в панели честно ограниченный набор разделов — и это создаёт **ложное ощущение разграничения доступа**, что хуже открытого отсутствия ролей.

### [H] `perms.dump()` молча отбрасывает неизвестные коды

Владелец выдаёт право с опечаткой (`code.approve` вместо `codes.approve`) → ответ 200, тост «Права сохранены», право не выдано. Сотрудник жалуется на 403, владелец уверен, что выдал. Нужно 422 на неизвестном коде.

### [H] `club_id` у админа есть, но нигде не применяется

Поле заведено в модели и принимается в API, но **ни один запрос не фильтруется по клубу**. Сотрудник одного клуба видит гостей, коды и очередь всей сети и может погашать коды чужих клубов. Поле в базе без проверки в коде — это не заготовка, а ловушка.

### [H] `codes.approve` в `OWNER_ONLY` ломает работу стойки

Подтверждать выплату может только владелец. При этом владелец в системе **ровно один** и второго создать невозможно (часть 5). Значит, в отпуске владельца очередь компенсаций замирает целиком, а коды гостей тем временем сгорают через 24 часа.

### [M] Нет права «только смотреть каталог»

`catalog.edit` — единственное право на достижения, награды и ленту. Чтобы посмотреть цены, нужно право их менять. Подробнее — в части 5 (`catalog.py`).

## 4. Вебхуки OASys (`webhooks.py`)

Маршруты: `/api/webhooks/oasys/{club_slug}/session-start`, `/session-end`, `/link-phone`. Авторизация — заголовок `X-OASys-Token`.

### [C] Токен — единственный фактор, и сравнивается он с открытым значением из БД

Нет ни подписи тела (HMAC), ни timestamp, ни nonce, ни списка разрешённых IP. Токен хранится в открытом виде и показывается в панели (блокер B). Любой, кто его увидел, получает полный контроль над начислениями.

### [C] `link-phone` позволяет перевешать телефон на чужой аккаунт

В отличие от бота (где есть проверка `contact.user_id`), здесь `telegram_id` и `phone` приходят от вызывающего и принимаются на веру. С утечённым токеном можно привязать номер жертвы к своему `telegram_id` и перехватыть её минуты и статус.

### [H] Нет ни дедупликации доставок, ни журнала вебхуков

Нет таблицы входящих событий. При проблеме невозможно ответить на вопрос «что именно прислал OASys» — а это главный вопрос при любом споре о начислениях. Нужен inbox с сырым телом, временем и результатом обработки.

### [H] `UserNotLinked` отдаёт ошибку, и OASys будет ретраить вечно

Гость без привязки — это **нормальная ситуация** (большинство посетителей клуба не в программе), а не ошибка. Ответ должен быть 200 с `{"status": "ignored"}`, иначе очередь ретраев у вендора забивается штатными событиями.

### [H] Log injection в логах вебхука

`session_id` и `club_slug` подставляются в строку лога без очистки, а `session_id` — строка без ограничения длины и без запрета переводов строки (часть 5). Можно подделать строки журнала.

### [M] `club_slug` в пути — перебор существующих клубов

Несуществующий slug даёт 404, неверный токен — 401/403. Разные коды позволяют перебрать список клубов сети без авторизации.

### [M] Нет ограничения частоты на вебхуках

Каждый вызов `session-end` тянет за собой ачивки, рефералов и запись в SQLite с блокировкой файла.

## 5. Мини-апп API (`miniapp.py`)

### [C] Чтение меняет данные

- `GET /api/me` → `achievements.overview()` → создаёт строки прогресса и **коммитит**
- `GET /api/rewards` → `expire_due()` → меняет статусы и **возвращает PTS**

Следствия: двойной возврат при параллельных чтениях, рост таблицы прогресса от простых просмотров, невозможность кэшировать GET.

### [H] Ни одного `response_model`

Ни в одном роутере нет `response_model`. Все ответы — ручные словари. Следствия:

- `/docs` показывает пустые схемы ответов — фронтендер угадывает контракт
- Ничто не мешает будущему хендлеру вернуть ORM-объект целиком — с `password_hash` включительно
- Нет единого контракта ошибок → фронтенд получает `[object Object]` на 422 (часть 4)

### [H] `/docs` и `/openapi.json` открыты

Вся поверхность API, включая `/api/console/test/*` и `/api/admin/*`, публично документирована. В паре с дефолтным `admin_token` это готовая инструкция.

### [M] `/api/achievements/check-subscription` — синхронный вызов Telegram внутри запроса

Нет ни таймаута в ответе гостю, ни кэша результата, ни ограничения частоты — кнопку «Проверить подписку» можно жать бесконечно.

### [M] `/api/history/visits` и `/pts` — жёсткий `limit`, нет пагинации

Гость с годами истории видит последние 200 записей и никак не узнаёт, что есть ещё.

### [M] Нет `ETag` / `Cache-Control` ни на одном чтении

А `refreshAll()` в мини-аппе делает четыре последовательных запроса после каждого действия (часть 4).

## 6. Админские ручки (`admin.py`, `desk.py`, `console.py`)

### [H] `POST /api/console/users/{telegram_id}/pts?amount=...&comment=...`

Сумма и комментарий передаются **query-параметрами** в POST. Следствия: сумма начисления попадает в логи доступа веб-сервера, в историю браузера и в Referer. Для денежной операции — недопустимо.

### [H] Две разные реализации ручного начисления PTS

`admin.py` и `manage.py` делают одно и то же разным кодом: разные проверки прав, разный аудит, разное поведение на отрицательной сумме (одна из них даёт 500).

### [H] N+1 в `GET /api/console/users`

На каждую строку страницы (30 шт.) вызываются `year_stats` и расчёт группы — то есть десятки запросов с `LIKE` по сессиям на каждое открытие списка.

### [H] Поиск на стойке принимает wildcard гостя

`q` подставляется в `LIKE` без экранирования `%` и `_`. Запрос `%` возвращает всё целиком — полный дамп гостевой базы с телефонами для любого с `codes.view`.

### [M] `GET /api/console/logs?page_size=100` без верхней границы

`page_size` не ограничен — `?page_size=1000000` вытянет весь журнал в память.

### [M] Отчёты без ограничения диапазона

`date_from` / `date_to` не проверяются ни на порядок, ни на ширину. Пустой диапазон = вся история сети в память (см. `network_summary` в части 3).

### [M] `/api/console/sheets/check` меняет таблицу

Ручка называется «проверить доступ», а фактически может создать лист и записать шапку (часть 3). Название вводит в заблуждение.

### [M] Отсутствует страница «Коды» в навигации

`showView('codes')` существует и разметка есть, но пункта меню нет — раздел недостижим (подробно в части 4).

## 7. `main.py` и общая обвязка

### [H] Демо-гейт отвечает HTML на API-запросы

`_DEMO_LOGIN_PAGE` отдаётся с кодом 401 **на любой путь**, включая `/api/*`. Фронтенд делает `JSON.parse(text)` без защиты (часть 4) → **в демо-режиме все запросы мини-аппа умирают с ошибкой разбора**, а не с понятным сообщением.

### [M] CORS и заголовки безопасности

Нет `Content-Security-Policy`, `X-Frame-Options` (а мини-апп живёт во фрейме Telegram — нужен аккуратный `frame-ancestors`), `X-Content-Type-Options`, `Referrer-Policy`. Отсутствие CSP прямо повышает серьёзность XSS-находок из части 4.

### [M] Монтирование `/` → `miniapp/`

Статика отдаётся с корня тем же процессом, без кэш-заголовков — отсюда ручное `?v=6` в шести местах (часть 4).

### [M] Нет единого обработчика исключений

`SessionIngestError`, `CatalogError`, `AdminError`, `WheelError`, `InsufficientFunds`, `AchievementError` обрабатываются в каждом хендлере по-своему или не обрабатываются вовсе → 500 с внутренним текстом, который фронтенд показывает гостю буквально.

### [L] Нет `/healthz`

Нечем проверять живость и готовность при развёртывании.
