## 0. Корректировки прежних выводов

Пятая часть исходников закрыла ряд вопросов из частей 1–4. Ниже — честные снятия и понижения.

| Прежняя находка | Новый статус | Причина |
| --- | --- | --- |
| `kind=reward` с пустым `reward_id` крадёт PTS | [C] → [M] | `catalog._validate_prize` блокирует и на создании, и на обновлении |
| Форма приза в админке ворует PTS | [H] → [M] | Валидатор отклонит сохранение; остаётся плохой UX |
| `cost_pts=0` → бесплатные прокрутки | [C] → [M] | `create_wheel` и `update_wheel` требуют положительную стоимость |
| `target=0` → `NaN%` | [H] → [L] | Валидатор требует положительное значение |
| Смена `period` роняет `/api/me` | достижимо иначе | Через API нельзя, но `seed.py --force` перезаписывает напрямую |
| `admins.payload()` утекает `password_hash` | снято | Хеш не попадает в ответ |
| Владелец может удалить или отключить сам себя | снято | Есть явные проверки на владельца |
| `SpinRequest.count` не ограничен | снято | Поле объявлено как `Literal[1, 5, 10]` |
| `ClubCreateRequest.slug` не валидируется | снято | Есть корректный паттерн |

## 1. Telegram-бот (`bot/main.py`)

### [C] Реферальная ссылка не запрашивает телефон

Обработчик `start_with_referral` привязывает код и отправляет кнопку запуска приложения, но не показывает клавиатуру запроса контакта. Обычный `/start` — показывает. Следствие: **гость, пришедший по реферальной ссылке, никогда не привязывает телефон**, значит вебхуки OASys его не находят, минуты не начисляются, реферальный зачёт не срабатывает никогда. То есть весь реферальный механизм в текущем виде нерабочий по своему главному пути входа.

### [C] Уведомления не существуют

Функция `notify()` объявлена, но **не вызывается ни из одного места проекта**. Ни один сценарий не доходит до пользователя: код готов, код сгорает через 24 часа, ачивка выполнена, награда подтверждена, реферал зачтён. В паре с нетикающим таймером в интерфейсе (часть 4) это означает, что гость узнаёт о сгорании оплаченной награды только придя на стойку.

### [H] Блокирующий синхронный доступ к БД в async-хендлерах

`_get_or_create`, `start`, `save_contact` вызывают синхронный SQLAlchemy прямо в корутине. При SQLite с файловой блокировкой один медленный запрос останавливает весь event loop бота. Плюс внутри пути создания пользователя работает `referrals.generate_code` с циклом SELECT-ов без предела итераций (часть 3).

### [H] `save_contact` не обрабатывает конфликт по телефону

`phone` уникален. Если номер уже привязан к другому аккаунту, происходит `IntegrityError`, который никто не ловит: пользователь не получает **никакого** ответа, а клавиатура остаётся. Это штатный сценарий — один номер, два Telegram-аккаунта.

### [H] Четыре расходящиеся реализации get-or-create пользователя

Бот, `auth.py`, `sessions.resolve_user` и `_ensure_test_user` создают пользователя по-своему: разные поля по умолчанию, разное поведение при гонке, разный реферальный код. Любая правка правил регистрации требует четырёх синхронных изменений.

### [M] Гонка SELECT-then-INSERT

Без обработки `IntegrityError`. Двойное нажатие `/start` даёт дубль или ошибку.

### [M] Нет запасного пути для телефона текстом

Если пользователь отклонил доступ к контакту или ввёл номер текстом, бот не понимает ввод и не подсказывает.

### Верифицировано как корректное

Проверка `message.contact.user_id == message.from_user.id` — правильная и важная: она не даёт переслать чужой контакт и привязать чужой номер. Ровно этой проверки не хватает вебхуку `link-phone` (часть 2).

### [M] Инициализация бота

`Bot()` создаётся без `DefaultBotProperties` и без режима разметки — форматирование сообщений будет вести себя непредсказуемо. Нет graceful shutdown, нет тротлинга, нет FSM. Оба процесса (API и бот) независимо вызывают `init_db()`. `miniapp_url` подставляется в `WebAppInfo` без валидации. Длинный поллинг запускается без защиты от второго экземпляра — два процесса будут разбирать сообщения по очереди.

## 2. Игровые сессии (`sessions.py`)

### [C] Идемпотентность — это SELECT без обработки конфликта

`_find` ищет сессию по `oasys_session_id`, и при отсутствии создаётся новая. Обработки `IntegrityError` нет. Два параллельных ретрая одного вебхука (что для OASys норма) дают вечный 500: первый вставляет, второй падает на уникальном ограничении и падает снова при каждом повторе.

### [C] Опора на ограничение, которого может не быть в проде

Вся защита от дублей держится на `uq_session_per_club`. Схема создаётся через `create_all`, а колонки досинхронизируются `sync_sqlite_columns` — **ограничения при этом не добавляются**. Если таблица создана более старой версией кода, ограничения в развёрнутой базе может не быть, и никто об этом не узнает. Проверьте на живом стенде через `PRAGMA index_list`.

### [C] Повторный `session-start` с другими данными молча игнорируется

Если пришла сессия с тем же идентификатором, но другим `pc_number` или другим гостем, изменения не применяются и ошибка не возвращается. При коллизии идентификаторов между гостями это означает начисление минут не тому человеку — без единого следа.

### [H] `duration_minutes` принимается на веру

Единственное ограничение — неотрицательность. Ни верхней границы, ни сверки с `started_at` и `ended_at`. С утечённым токеном вебхука (блокер B части 2) одна строка запроса даёт группу «Легенда» и все минутные ачивки.

### [H] Нет проверки `ended_at >= started_at`

Отрицательная длительность сессии проходит, попадает в статистику и в отчёты.

### [H] `is_closed` делает исправления невозможными

Закрытая сессия не может быть скорректирована. Если OASys прислал неверную длительность, единственный путь — правка БД руками.

### [H] `started_at` не ограничен ни в прошлое, ни в будущее

Сессия с датой из будущего или из 2019 года принимается и учитывается в периодах.

### [H] Реферальный зачёт вызывается до коммита

`referrals.on_session_closed` выполняется внутри `end_session` до фиксации. Отсутствие ачивки `special_referral` в БД → исключение → полный откат закрытия сессии → 500 → бесконечные ретраи вендора (часть 3).

### [M] Пересоздание сессии в `session-end`

Если сессии нет, она создаётся с `pc_number`, который в тестовой форме по умолчанию равен 1 (часть 4). Это ставит ложные отметки зон в ачивках «поиграй во всех зонах».

### [M] `resolve_user` пишет в БД внутри резолвера

Функция с именем «разреши пользователя» создаёт пользователя. Тот же системный паттерн, что `overview()` и `expire_due()`.

### [M] `normalize_phone` работает только для России и теряет данные

Логика заточена на 11 цифр с ведущей 7 или 8. Любой другой формат нормализуется непредсказуемо, а исходное значение не сохраняется.

### [M] `year_stats`: визиты и часы считаются по разной логике

Визиты и суммарные часы берутся из разных выборок, поэтому «5 визитов, 0 часов» — достижимое состояние на экране гостя.

### Верифицировано как корректное

Сам путь приёма вебхука атомарен относительно начисления PTS: списание и запись транзакции идут в одной транзакции. Это сделано верно.

## 3. Схемы данных (`schemas.py`)

### [C] Все перечисления — свободные строки

`kind`, `payout_unit`, `rarity`, `unit`, `category` объявлены как `str` без `Literal`. Следствия:

- Опечатка в `kind` создаёт приз, который не разбирается ни одной веткой `_resolve_one` → гость платит и не получает ничего
- Опечатка в `payout_unit` меняет отображаемую сумму и уезжает в таблицу выплат
- Опечатка в `rarity` ломает сортировку и подсветку в интерфейсе

Замена этих пяти полей на `Literal` — это несколько строк, которые закрывают денежный баг.

### [H] Нет проверки `payout_value >= 0` нигде

Ни в создании награды, ни в обновлении. Награда с отрицательной выплатой создаётся, выдаётся гостю и попадает в таблицу компенсаций.

### [H] `unit` — свободная строка, а фронтенд делит на 60

Если единица равна `мин`, клиент пересчитывает значение в часы. Опечатка в единице меняет показанное число в 60 раз (часть 4).

### [H] `session_id` без ограничений

Нет `min_length`, нет `max_length`, нет запрета переводов строки. Пустая строка сводит все сессии клуба в одну запись. Переводы строки дают подделку журнала (часть 2).

### [H] `phone` и `client_id` без ограничений длины

Прямой путь к раздуванию базы и к проблемам с уникальным индексом по телефону.

### [H] `SessionStartPayload` несёт `ended_at` и `duration_minutes`

Поля завершения в схеме старта, и `duration_minutes` без верхней границы. Схема не отражает предметную область и открывает путь мгновенной «Легенды».

### [M] `pc_number` ограничен 49 в схеме

Число дублирует `TOTAL_PCS = 49` из модуля зон. Два источника истины для одного факта — при расширении клуба забудут одно из мест.

### [M] Пароль входа без `max_length`

Прямой путь к CPU-DoS через PBKDF2 с 310 000 итераций (часть 2).

### [M] `username` без паттерна

Пробелы, регистр, кириллические омоглифы. В паре с регистронезависимой записью и регистрозависимым чтением (см. раздел 5) это путь к путанице учётных записей.

### [M] `GrantPtsRequest.amount` без границ

Отрицательное значение уходит в `pts.credit` и даёт 500 вместо понятной ошибки.

### [M] `permissions` фильтруются молча

Неизвестный код прав отбрасывается, ответ 200. Владелец уверен, что право выдал (часть 2).

### [M] Деньги как `float` в схемах

Сквозная проблема проекта: денежные значения должны быть целыми копейками или `Decimal`.

### [M] `weight = 0` допустим для всех призов

Если все веса нулевые, генератор рулетки не может выбрать приз — 400 для каждого гостя. Нужна проверка суммы весов на уровне колеса, а не отдельного приза.

### [M] Ни одного `response_model`

Схемы описывают только вход. Контракт ответа нигде не зафиксирован (часть 2).

## 4. Инициализация данных (`seed.py`)

### [C] Клуб по умолчанию получает токен `change-me`

Вебхук-эндпоинт публичен, а единственный фактор авторизации — этот токен. Развёртывание «по инструкции» открывает начисление минут кому угодно. Нужна генерация случайного токена и отказ стартовать с дефолтным значением.

### [C] Владелец создаётся с паролем `change-me-now`

Единственная защита — предупреждение в консоли, которое в логах развёртывания никто не читает. В паре с отсутствием rate-limit на входе (часть 2) это полный доступ к панели за один запрос.

### [H] `--force` — единственный доступный путь изменить `period`

Через API поле недоступно, поэтому владелец будет пользоваться `--force`. И это единственный реальный путь к падению `/api/me` из части 3.

### [H] `--force` откатывает согласованные цены к заготовкам

Флаг перезаписывает награды и колесо значениями из кода. Владелец, поменявший стоимость наград под свою экономику, потеряет настройки при следующем запуске сидера с флагом. Никакого предупреждения нет.

### [H] Арифметика отдачи в докстринге неверна

В комментарии заявлено 26 500 PTS выплат на 100 прокруток, то есть 88 процентов. Считаем по фактическим весам колеса (40 + 30 + 15 + 5 + 10 = 100):

| Приз | Вес | Выплата | Итог на 100 прокруток |
| --- | --- | --- | --- |
| 100 PTS | 40 | 100 | 4 000 |
| 250 PTS | 30 | 250 | 7 500 |
| 600 PTS | 15 | 600 | 9 000 |
| 1500 PTS | 5 | 1500 | 7 500 |
| Пусто | 10 | 0 | 0 |
| **Всего** | 100 |  | **28 000** |

Сбор при стоимости 300 PTS: 30 000. Реальная отдача — **93,3 процента**, а не 88. Разница — 1 500 PTS на каждые 100 прокруток, и она работает против клуба. Владелец принимает решения об экономике по числу в комментарии, которое неверно, и по метрике `payout_percent`, которая не учитывает рублёвые призы (часть 3). Две независимые ошибки в одну сторону.

### [M] Хрупкий порядок инициализации админов

`seed_default_admin` и `ensure_owner` работают в правильном порядке только потому, что сессия создана с `autoflush=False`. Неочевидная зависимость, которая сломается при рефакторинге.

### [M] Нет версионирования схемы и данных

Ни Alembic, ни таблицы версий сидов. Повторные запуски и частичные обновления невоспроизводимы.

### [M] `Reward(**item)` без валидации

Словари из кода разворачиваются прямо в модель, минуя схемы и проверки каталога.

### [M] Разная цена PTS за рубль в наградах

3000 PTS за 300 рублей, 4750 за 500, 9000 за 1000 — то есть 10, 9,5 и 9 PTS за рубль. Прогрессия задумана, но нигде не задокументирована и не объяснена гостю.

## 5. Каталог и администраторы (`catalog.py`, `admins.py`)

### Верифицировано как корректное

- `payload()` **не** раскрывает `password_hash` — прежнее замечание снимаю
- Владелец защищён от ограничения прав, отключения и удаления — прежнее замечание снимаю
- Мягкое удаление наград (`is_active`) вместо физического — верное решение, история кодов не рвётся
- `_validate_prize` валидирует уже слитые значения, а не только присланные — правильный порядок, именно он закрывает три бага из частей 3 и 4
- `is_implemented` намеренно нередактируемо — верно, это свойство кода, а не данных

### [H] Второго владельца создать нельзя, и запасного входа нет

Роль не принимается ни в создании, ни в обновлении (это правильная защита от эскалации), но альтернативного пути тоже нет. `ensure_owner` повышает кого-то только когда владельца нет вовсе. Следствия: `codes.approve` доступен ровно одному человеку, и в его отпуске очередь компенсаций замирает, а коды гостей сгорают.

### [H] `delete()` — физическое удаление

Два последствия. Первое: имена в журнале действий превращаются в висячие ссылки, и история проверок теряет автора. Второе: SQLite переиспользует rowid, а идентификатор сессионной куки — это `admin_id`. Значит **старая кука уволенного сотрудника аутентифицирует нового администратора с теми же правами**. Нужно мягкое удаление.

### [H] `CATALOG_EDIT` — одно право на всю экономику

Достижения, награды, колёса и призы. Сотрудник, которому нужно поправить описание ачивки, получает право менять стоимость наград и вероятности призов. Нужно разделить на просмотр и правку и выделить экономические поля отдельно.

### [M] Логин записывается без учёта регистра, а читается с учётом

Создание приводит логин к нижнему регистру, а поиск при входе — нет. Сотрудник, введя логин с заглавной буквы, получает «неверные данные» при корректном пароле.

### [M] `display_name` и `club_id` владельца редактируемы

Остальные поля защищены, эти — нет. Непоследовательно.

### [M] `set_password` не отзывает сессии

Подтверждено на уровне сервиса. Смена пароля не выкидывает уже вошедших (часть 2).

### [M] Политика пароля — только длина 8

Нет проверки на словарные пароли, нет запрета совпадения с логином, нет требования смены дефолтного.

### [M] Коммит в каждой функции ломает атомарность аудита

Сервис коммитит сам, вызывающий код пишет журнал и коммитит второй раз (часть 3).

### [M] `update_reward` меняет единицу и сумму при живых кодах

Снапшот в кодах защищает выданные, но админ не видит предупреждения, что на руках есть непогашенные коды с прежними условиями.

### [L] `create_prize` не проверяет существование награды

Последний оставшийся путь к битой ссылке на награду в призе — идентификатор несуществующей или неактивной награды не проверяется на существование.
