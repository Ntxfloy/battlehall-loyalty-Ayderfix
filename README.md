# BATTLEHALL — программа лояльности

Telegram Mini App + бэкенд поверх клубного софта **OASys**. Реализовано по спеке
`loyalty_app_spec.md`: слой геймификации подключается к уже существующим вебхукам
сессий и привязке Telegram ↔ телефон.

Стек: Python 3.12+, FastAPI, SQLAlchemy 2, SQLite для разработки и Postgres в проде.
Фронт — без сборки: обычные HTML/CSS/JS плюс Telegram WebApp SDK, поэтому Node в
проекте не нужен вообще, а мини-апп отдаётся тем же процессом, что и API.
Оформление — по брендбуку клуба (`static/brand/`).

## Быстрый старт

```bash
python -m venv .venv && .venv/Scripts/python.exe -m pip install -r requirements.txt
```

```bash
cp .env.example .env && .venv/Scripts/python.exe seed.py && .venv/Scripts/python.exe run.py
```

Дальше:

* мини-апп — http://localhost:8000
* **админ-панель — http://localhost:8000/admin/** (логин/пароль из `ADMIN_DEFAULT_USERNAME`/`ADMIN_DEFAULT_PASSWORD` в `.env`)
* доки API — http://localhost:8000/docs
* бот (нужен `BOT_TOKEN`) — `.venv/Scripts/python.exe -m bot.main`

`seed.py` при первом запуске создаёт клуб `main` (токен вебхука = `OASYS_WEBHOOK_TOKEN` из `.env`) и первого администратора. Оба шага пропускаются, если в базе уже что-то есть — безопасно гонять `seed.py` повторно.

В `.env` по умолчанию стоит `DEV_ALLOW_FAKE_AUTH=true`: без подписи Telegram
приложение открывается под тестовым пользователем. **На проде это выключить**,
иначе любой запрос без заголовка станет валидным.

Тесты:

```bash
.venv/Scripts/python.exe -m pytest -q
```

### «ЛУДЛЕНТА»

Гость платит PTS за прокрутку и получает случайный приз. Приз может быть
начислением PTS, награждением кодом из каталога или пустой ячейкой —
состав, редкость и веса задаются в панели, движок про конкретные призы
ничего не знает.

Два решения, которые стоит понимать:

* **Победитель определяется на сервере.** Клиент получает готовый результат
  и ленту для анимации — иначе выигрыш подделывался бы в браузере.
* **Розыгрыш идёт на `secrets`, а не на `random`.** Обычный генератор
  предсказуем по предыдущим результатам, а тут разыгрываются деньги клуба.

Шанс каждой ячейки виден гостю (`вес / сумма весов`) — механика не должна
выглядеть чёрным ящиком. Фактическую отдачу ленты владелец видит в
`/api/console/wheels/{id}/stats`: сколько PTS потрачено против выигранного.

### Админ-панель — http://localhost:8000/admin/

Вход по логину/паролю (учётка в таблице `admin_users`, пароль — PBKDF2-хеш,
без внешних зависимостей вроде bcrypt). Сессия — подписанная HTTP-only кука
на `ADMIN_SESSION_TTL_HOURS` часов.

* **Обзор** — сводка по сети: пользователи, сессии, часы по каждому клубу.
* **Стойка** — одно поле поиска: код, ник, имя или телефон. Показывает
  код, гостя и его телефон, кнопкой вносит код. Это единственный раздел,
  который нужен аккаунту на администраторском ПК клуба.
* **Подтверждение** — очередь внесённых кодов. Подтверждает только владелец;
  до подтверждения строка не попадает в выгрузку для таблицы компенсаций.
* **Пользователи** — поиск по имени/нику/телефону/telegram_id, в карточке —
  визиты, история PTS, выполненные достижения, обмены на награды.
* **Достижения** — названия, цели, награды, вкл/выкл. Способ подсчёта в панели
  не меняется: он задан в коде, и достижения без счётчика помечены явно.
* **Награды** — создание и правка каталога. Удаление сделано выключением:
  на награду ссылаются уже выданные коды и призы ленты.
* **ЛУДЛЕНТА** — ленты, призы, веса и пересчитанные шансы.
* **Клубы** — создать клуб сети (генерирует токен вебхука), включить/выключить,
  перевыпустить токен.
* **Отчёты** — сессии/часы/уникальные гости по каждому клубу за период, с
  разбивкой по типам зон. PTS и награды не разбиты по клубам намеренно —
  это общий кошелёк на всю сеть (гость копит и тратит их в любом клубе).
* **Администраторы** — завести учётку и выдать ей права галочками.
* **Тестовые запросы** — отправить `session-start`/`session-end` без реального
  OASys, прямо на движок достижений; если гостя ещё нет в базе, панель заведёт
  тестовую запись сама (в отличие от настоящего вебхука, который таких молча
  пропускает).
* **Журнал действий** — кто и когда внёс код, подтвердил его, начислил PTS.

### Роли: владелец и стойка

Владелец один, его права неизменяемы и отключить его нельзя — иначе панель
осталась бы без администратора. Остальные учётки — сотрудники, права им
выдаёт владелец в разделе «Администраторы».

Два права сотруднику выдать невозможно (`app/permissions.py:OWNER_ONLY`):
подтверждение кодов и управление учётками. В этом и смысл разделения —
сотрудник вносит код, но не подтверждает сам себя.

Панель прячет разделы, на которые прав нет, но полагаться на это нельзя:
доступ проверяется на каждой ручке отдельно.

**Путь кода:** `pending` (гость получил) → `submitted` (сотрудник внёс на
стойке) → `approved` (владелец подтвердил). В выгрузку `/api/admin/redemptions`
идут только `approved`. Отклонённый код возвращается гостю, если ещё не сгорел.

### Живые данные из внутреннего API OASys

Отдельно от вебхуков (те приходят от OASys сами, по событию сессии) есть
обратная связка: сервер сам дёргает внутренний API OASys — тот же, которым
пользуется официальный Windows-клиент админа зала. Публичной документации
у этого API нет, эндпоинты вскрыты перехватом собственного авторизованного
трафика клиента через Fiddler (`oASys_bot/oASys/*.har`).

Нужно для внутренней демки: живая карта зала (кто где сидит, свободные ПК)
поверх уже работающей карты зон, без ожидания вебхуков, плюс касса и скидки
на одном экране.

Ручки (`app/services/oasys_live.py`, права `oasys.view`):

* `GET /api/console/oasys/map` — занятость по каждому ПК + название зоны
  программы лояльности (учитывает `?club_id=` для клубов с переопределением
  карты зон).
* `GET /api/console/oasys/cashier-stats` — статистика текущей смены кассы.
* `GET /api/console/oasys/discounts` — клубные скидки и промокоды.

Интеграция необязательная, как и Google Sheets: без `OASYS_JWT`/`OASYS_PC_JWT`
в `.env` ручки отдают понятную ошибку (502), остальное приложение работает
как обычно. Раздела в панели под это ещё нет — только API.

### Google Sheets

Подтверждённые компенсации уезжают в таблицу автоматически. Доступ — через
**сервисный аккаунт Google**, а не личный OAuth: серверу нужно писать без
участия человека, а пользовательский токен пришлось бы обновлять руками.

Что нужно сделать один раз:

1. В [Google Cloud Console](https://console.cloud.google.com/) создать проект
   и включить в нём **Google Sheets API**.
2. Создать **сервисный аккаунт**, в нём — ключ формата JSON, скачать файл.
3. Положить файл в `secrets/google-service-account.json` (папка в `.gitignore`).
4. Создать таблицу и **дать доступ на редактирование** тому e-mail, что указан
   в ключе как `client_email` — иначе сервисный аккаунт таблицу не увидит.
5. В `.env` заполнить `GOOGLE_SHEET_ID` (часть ссылки между `/d/` и `/edit`)
   и `GOOGLE_CREDENTIALS_FILE`.

Проверить связку — кнопка «Проверить доступ» в разделе «Подтверждение».
Лист с названием из `GOOGLE_SHEET_WORKSHEET` создаётся сам, вместе с шапкой.

Ключевое в надёжности: `exported_at` проставляется **только после успешной
записи**. Если Google недоступен, подтверждение кода всё равно проходит, а
строка остаётся в очереди и уедет следующей выгрузкой — ни потерь, ни дублей.

Без настроек интеграция просто выключена: выгрузка отдаёт JSON для ручного
переноса, всё остальное работает как раньше.

Существующие `/api/admin/*` ручки (для скриптов и выгрузки в гугл-таблицу)
продолжают работать по `X-Admin-Token` — панель их не заменяет, а делит с ними
объект защиты (`app/admin_auth.py:require_admin` принимает и токен, и куку).

### Достижения, которые считаются сами

Всё, что выводится из вебхуков сессий: ежедневный чек-ин, часы за неделю,
разные дни недели, 15 разных дней за месяц, все 5 зон за месяц, реферал,
подписка на канал, накопительные PTS.

### Достижения, помеченные «Скоро»

Видны в каталоге, но счётчик не подключён — нет источника данных:
пакеты часов 3ч/5ч и игра по брони (нужны вебхуки покупок и брони из OASys),
заказы бара (нет интеграции с Эвотором — вне MVP по спеке), тарифы
УТРО/ДЕНЬ/НОЧЬ (нужен тип тарифа в вебхуке), опрос (нужна форма).

Подключение каждой из них — это одна строка в `app/achievements_defs.py`
(поменять `rule`) плюс вызов `achievements.increment(...)` из нового обработчика.

## Что нужно от команды OASys

Путь вебхука содержит slug клуба сети (у каждого клуба свой токен — берётся
в панели на вкладке «Клубы»): `POST /api/webhooks/oasys/{club_slug}/session-start`,
заголовок `X-OASys-Token` со значением токена этого клуба.

`POST /api/webhooks/oasys/main/session-start`

```json
{
  "session_id": "12345",
  "pc_number": 12,
  "started_at": "2026-08-20T18:17:07Z",
  "telegram_id": 100001,
  "phone": "+79990000000",
  "client_id": "oasys-777"
}
```

`POST /api/webhooks/oasys/main/session-end` — то же плюс `ended_at` и, если есть,
`duration_minutes`.

Гостя ищем по `client_id` → `telegram_id` → `phone`, достаточно любого одного.
Если гость ещё не в программе лояльности, ответ — `200 {"status": "skipped"}`:
это не ошибка, ретраить не нужно. Повторная доставка того же `session_id`
безопасна — но только в рамках одного клуба: у двух клубов сети `session_id`
может случайно совпасть (разные независимые инсталляции OASys), это не считается
дублем. Если событие старта потерялось, сессия восстановится из события конца.

Третья ручка, `POST /api/webhooks/oasys/main/link-phone`, принимает связку
Telegram ↔ телефон из существующего бота — чтобы не просить у гостя номер второй раз.
Она не клубная по смыслу (аккаунт гостя один на всю сеть), slug в пути нужен
только для проверки токена.

```
  loyalty.py            группы лояльности по часам за год

  models.py             схема БД
  auth.py               проверка подписи Telegram (гость)
  admin_auth.py         логин/пароль, кука сессии, проверка прав
  permissions.py        каталог прав; какие нельзя выдать сотруднику
  schema_sync.py        досинхронизация колонок SQLite (заменится Alembic)
  services/
    sessions.py         приём вебхуков, статистика (в разрезе клуба)

    pts.py              баланс и журнал
    rewards.py          обмен, коды, сгорание
    referrals.py        приглашения
    clubs.py            справочник клубов сети, отчётность
    audit.py            журнал действий администраторов
    admins.py           учётки администраторов
    catalog.py          правка достижений, наград и ЛУДЛЕНТЫ
    wheel.py            розыгрыш ЛУДЛЕНТЫ, выдача призов
    oasys_live.py        живые данные из внутреннего API OASys (не вебхуки)
  api/
    miniapp.py          то, что дергает фронт гостя
    webhooks.py         то, что дергает OASys (путь /oasys/{club_slug}/...)
    admin.py            служебные ручки наград/PTS — токен или кука
    console.py          API самой панели: auth, обзор, users, clubs, logs, reports, test, живые данные OASys
    desk.py             стойка клуба: поиск гостя, внесение и подтверждение кода
    manage.py           правка достижений/наград/ЛУДЛЕНТЫ и учёток администраторов
miniapp/                фронт гостя: index.html + styles.css + app.js
admin/                  фронт админки: + sections.js (стойка, каталог, роли)
static/brand/           фирменный слой: токены, логотип, паттерн, шрифты
bot/main.py             бот-компаньон
```

Два принципа, на которых держится остальное:

1. **Прогресс живёт в разрезе периода.** У строки прогресса есть `period_key`
   (`2026-W34`, `2026-08`, `2026-08-20`). Поэтому «обнуления по понедельникам»
   как отдельной задачи нет — в 06:00 МСК просто начинает заполняться строка
   с новым ключом, а старая остаётся в истории.
2. **PTS двигаются только через `services/pts.py`.** Баланс в `users` —
   денормализация; источник правды — журнал `pts_transactions`, в котором
   у каждой операции есть причина и ссылка на объект.

## Решения, которые стоит перепроверить с клубом

Это не белые пятна, а места, где я выбрал разумный вариант сам. Поменять
каждое — минуты, но лучше подтвердить до запуска.

1. **PTS возвращаются, если код сгорел неиспользованным** (`REFUND_PTS_ON_EXPIRE=true`).
   В спеке это стояло как открытый вопрос. Сделал возврат: сгоревшие PTS без
   возврата читаются гостем как обман.
2. **Одновременно активен только один код награды.** Иначе на стойке спор,
   какой из трёх кодов гость сейчас гасит.
3. **Экономика — заглушка.** Цены наград (`seed.py`), суммы PTS за ачивки и
   пороги групп лояльности (`app/loyalty.py`) выставлены по мотивам скриншотов
   Oblaka. Реальные цифры должен утвердить клуб; правятся без релиза, кроме
   групп лояльности.
4. **Приглашение друга — разовая ачивка.** Как в «Особых» у Oblaka. Если нужно
   платить за каждого друга, механику надо переделывать: сейчас второй и третий
   друг не приносят ничего.
5. **Незабранная награда сгорает вместе с периодом.** Следует из правила
   «награду нужно забирать вручную» — но гостю это стоит показать заметнее,
   чем строкой в правилах.
6. **Сессии гостей вне программы не сохраняются.** Если человек установит
   мини-апп позже, его прошлые визиты не подтянутся. Чинится бэкфилом из OASys,
   если это нужно на старте.
7. **Карта ПК → зона общая для всех клубов**, если для конкретного клуба не задано
   переопределение (`Club.pc_zone_overrides`, JSON `{"1": "DUO_A", ...}` — задаётся
   пока напрямую в БД, ручки в панели для этого ещё нет). Для клуба из спеки
   всё верно из коробки; для второго клуба сети с другой раскладкой зала
   переопределение обязательно, иначе отчёт по зонам будет врать.
8. **PTS и награды — общий кошелёк на сеть, не на клуб.** Гость копит и тратит
   PTS в любом клубе сети; отчётность по клубам поэтому показывает только то,
   что физически привязано к визиту (сессии, часы, зоны), а не суммы PTS.

### Смена пароля администратора

В `.env` пароль читается только при создании первой учётки. Сменить пароль
существующему админу:

```bash
.venv/Scripts/python.exe -c "from app.admin_auth import hash_password; from app.db import SessionLocal; from app.models import AdminUser; db=SessionLocal(); a=db.query(AdminUser).filter(AdminUser.username=='admin').one(); a.password_hash=hash_password('НОВЫЙ_ПАРОЛЬ'); db.commit(); print('ok')"
```

## Что осталось до прода

* **Alembic.** Таблицы создаются через `create_all`, а недостающие колонки
